# Work Log

## Day 1 — 2026-09-12

### Goal
Build intuition for the raw data before writing any segmentation code.
Traced one session end-to-end against its ground truth.

### What we did
- Reviewed README.md and DATA_SCHEMA.md in full before touching data.
- Pulled gt_manifest.json, first ~30 events.jsonl lines, and manifest.json
  for session ses_20260630-121953-LAPTOP-R36BQBTE.
- Initial (WRONG) assumption: treated gt_manifest.json's process listing
  order (A, B, C...) as chronological. It is not — it's grouped by process
  code. Corrected by reading gt.jsonl directly, which is the real
  chronological event stream.
- Extracted gt.jsonl process-level transitions for the full session
  (process_started / switched_out / suspended / resumed / session_ended).

### Key findings
1. **First ~3.5 min of every session is pure test-harness noise** —
   procmine-agent launch banner, terminal Enter-key spam, Notepad/Chrome
   setup — before the actual first business process starts. Must be
   excluded from segmentation, not treated as a process.
2. **This is synthetic/scripted data** (confirmed via visible terminal
   banner: "procmine-desktop-agent... DWELL_SCALE=1.4... walk away"),
   generated by a script with tunable dwell time and injected noise
   (noise_rate, noise_blocks in gt_manifest/gt.jsonl run_config).
3. **`app_switch` events are heavily duplicated.** Verified via payload-level
   process_id + window_title comparison: dozens of consecutive app_switch
   events per burst report identical new_app/previous_app (same pid, same
   title) — a recording/UIA-polling artifact, not real switching. Must
   dedupe on (process_id, window_title) before using app_switch as a
   boundary signal — app_name alone is insufficient (would falsely merge
   distinct windows/processes sharing the same app_name).
4. **Once deduped, the first real app_switch in a burst DOES align closely
   with the gt-logged process start** (within ~0.4s in the one case checked:
   H started at 12:21:12.79, real Excel->Chrome switch at 12:21:12.40).
   Initial (WRONG) read before dedup was "no app_switch aligns with this
   boundary" — corrected once duplicates were filtered out.
5. **No dead time between processes.** Every switched_out -> started pair in
   the session has a ~2-3ms gap. Idle-time/gap thresholds are NOT a usable
   primary boundary signal for this dataset — contradicts our Day 0 plan,
   which assumed idle gaps would help mark boundaries. Dropped from the
   approach.
6. **process_switched_out does not always precede process_started** — e.g.
   two consecutive M executions, two consecutive G executions, and two
   consecutive H executions occur back-to-back with no switched_out event
   and (as far as checked) no app change either. This is the hardest known
   case so far: same process type, same app, different case, no signal
   we've found yet to mark the boundary. Flagged as OPEN — need more
   examples before designing a rule. Not yet solved.
7. **Suspend/resume is real and linked via `split_id`, not `case_id`.**
   Process B suspended at 12:25:11 (split_id: M1-B-split-1, phase implied
   1), resumed at 12:30:59 (same split_id, phase: 2). Its case_id changed
   between suspend and resume (PI-175009-002 -> PI-175009-003) — this looks
   like a generator artifact, not semantically meaningful. Any Dataset A
   validation of suspend/resume merging must join on split_id, not case_id.

### Decisions made
- Boundary detection will NOT rely on idle-gap thresholds as primary signal
  (contradicts original plan — revised).
- app_switch events must be deduped on (process_id, window_title) before
  use.
- The "same process repeats back-to-back, no app change" case is deferred —
  need 2-3 more examples before deciding how to handle it. Will revisit
  once the boundary scorer exists and we can see how often/where this
  occurs.
- First few minutes of every session (pre-first-process) must be explicitly
  excluded, not fed into the segmenter as a candidate segment.

### Not yet done / open questions
- Have not yet checked whether extracted_text or clipboard_change can
  disambiguate consecutive same-process executions with no app change.
- Have not yet checked a second session to see if these patterns
  generalize (everything above is from ONE session so far).
